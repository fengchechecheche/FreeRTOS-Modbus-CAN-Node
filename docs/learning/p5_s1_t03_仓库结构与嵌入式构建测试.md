## 1. 为什么项目五必须是独立仓库

项目三是 Linux 工业通信网关，项目五是运行在 STM32F446RE 上的 FreeRTOS 固件。两者可能以后通过 Modbus RTU 或 CAN 通信，但依赖、构建方式、故障边界和验收证据完全不同。

因此项目五使用独立 Linux 工作区。项目三成功不能证明项目五成功；项目五的空仓库或主机 smoke
也不能证明项目三联调完成。

## 2. 为什么权威环境放在 Ubuntu 24.04

专用发行版 `Ubuntu-24.04-STM32` 从纯净 Ubuntu 24.04 模板建立，只服务于项目五。源码和构建目录
位于 Linux 文件系统，避免 Windows 挂载盘的大小写、权限、文件监听和性能差异成为权威构建的一部分。

本轮用干净 PATH 验证所有命令均来自 `/usr/bin`，其中 `cc` 为 Ubuntu 原生入口，不再落到 Windows/Cygwin。Windows 工具以后可以辅助 CubeMX 或 ST-LINK，但必须单独记录环境，不能把结果混成一份证据。

## 3. 一个项目为什么有三种名字

未来远程仓库名 `FreeRTOS-Modbus-CAN-Node` 面向人阅读；本地目录 `freertos_modbus_can_node` 避免 shell 中的连字符和大小写混乱；CMake 标识也使用 `freertos_modbus_can_node`，便于目标与变量保持一致。

这三种角色不是随意重复命名。冻结映射后，脚本不得临时改成其他拼写。S1-T03 实施时远程仓库尚未
创建；到 T04 的 `[038]` 基线，Windows/Ubuntu 已通过同一远程 `main` 同步。历史状态不能写成当前状态。

## 4. 生成代码、第三方代码和自有代码怎样分开

项目自有逻辑放在 `app/`、`protocol/`、`sensors/`、`config/` 和 `test/host/`。未来 CubeMX 生成入口放在 `Core/`，HAL/CMSIS 放在 `Drivers/`，FreeRTOS 等第三方代码放在 `Middlewares/Third_Party/`。

这样分层有两个直接好处：第一，重新生成 CubeMX 代码时能清楚审查哪些文件改变；第二，`clang-format`、`clang-tidy` 和 `cppcheck` 默认只处理项目自有代码，不会大批改写厂商或第三方文件。本轮后三个目录尚未创建，因为 T03 不伪造 CubeMX 产物。

## 5. Toolchain file 和 Presets 各负责什么

`cmake/arm-none-eabi-gcc.cmake` 告诉 CMake 目标系统是通用 ARM，编译器是 `arm-none-eabi-gcc`，并给出 Cortex-M4F 的 CPU、Thumb 和浮点 ABI 参数。它还要求 CMake 的编译器探测只生成静态库，避免在还没有启动文件与系统调用时做无意义链接。

`CMakePresets.json` 负责给常用组合起稳定名字，并隔离输出目录。主机 Debug/Release 与固件 Debug/Release 各用独立目录，避免不同编译器或优化级别复用缓存。

## 6. 主机构建和交叉编译有什么不同

主机构建使用 x86_64 Ubuntu 编译器，生成能在该主机运行的测试程序。交叉编译使用 Arm GNU
Toolchain，目标是 Cortex-M4F，生成的对象不能在 x86_64 主机直接执行。

T03 的 ARM 探针只执行 `-c`：把一段 C 编译成可重定位对象。真实固件还需要 STM32F446RE 的 startup、链接脚本、系统初始化、HAL/CMSIS 和 FreeRTOS；这些必须由 T04 的真实工程提供。

## 7. CTest smoke 能证明什么、不能证明什么

S1-T03 当时的 `p5_host_smoke` 证明 CMake 能配置、Ninja 能构建、CTest 能注册与运行测试，
Debug/Release 输出隔离，且测试失败能向上返回非零状态。当前回归规模见 T02/T03 Release 证据。

它没有实现 Modbus 帧、CAN 信号、传感器采样、FreeRTOS 调度或寄存器访问。因此 1/1 passed 只能理解为“测试基础设施工作”，不能写成协议或固件功能通过。

## 8. 本次遇到的真实问题

Windows PowerShell 向 WSL 传递嵌套引号时曾破坏命令文本；改用逐条原生命令后恢复。`command -v` 是 shell 内建命令，不能直接由 `env` 当作外部程序执行；在干净 PATH 的 Bash 中调用后，全部路径复核成功。

首次复制还让普通文件带上了 `0755`，最终已统一为 `0644`，只保留脚本可执行。首次格式检查也准确报出 smoke 不符合默认风格；调整格式后，Debug/Release、CTest 和全部静态检查均重新通过。这些失败是验证入口有效的证据，不应从记录中删除。

## 9. 三层“通过”不能互相替代

第一层是主机 smoke：本轮 Debug/Release 各 1/1 passed，可以支持主机构建/测试基础设施候选通过。第二层是工具链探针：ARM 对象属性符合 v7E-M、Thumb-2、VFPv4-D16 和 hard-float，只能写 `toolchain_probe=pass`。

第三层 `PASS_CROSS_BUILD` 要求真实 STM32F446RE 工程完成 Debug/Release 固件链接，并保留 ELF/HEX/BIN、size 和哈希等证据。本轮没有这些输入，所以交叉构建仍为 false。硬件与通信验收又是更后的层级，不能由编译替代。

## 10. 后续 S1-T04 当时如何消费这个骨架

S1-T04 随后在仓库中加入经过审核的 `.ioc`，让 CubeMX 生成与 F446RE 匹配的启动文件、系统文件和
HAL/CMSIS，并引入链接脚本和最小固件目标。当前 `[038]` 已在此基础上完成 FreeRTOS、协议和
Release 软件候选；实物仍未入场。

当时的 S1-T04 不应重建父目录、不应另起近似仓库名，也不应改用项目三发行版掩盖依赖问题。该原则
在当前双端工作流中继续有效。
