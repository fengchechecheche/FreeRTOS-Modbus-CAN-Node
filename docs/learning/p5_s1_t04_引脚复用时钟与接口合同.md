# P5-S1-T04 引脚复用、时钟与接口合同教程

> 教程状态：已审核固化（P5-S1-T04 `PASS`）
> T04 公开恢复说明：正文保留 S1-T04 当时的配置决策；当前软件/硬件边界见

## 1. `.ioc` 是配置合同，不是功能完成证明

`.ioc` 固定 MCU、引脚、时钟和外设初始化输入。它能证明 CubeMX 接受这组配置，但不能证明 Shield 已接对、总线可通信、传感器可读或协议已实现。本任务因此把硬件状态保留为 `WAITING_FOR_HARDWARE`。

## 2. 三类资料分别回答什么

NUCLEO 用户手册回答板载 ST-LINK、VCP、LED、按钮和排针连接；STM32F446 数据手册回答 MCU 引脚的复用功能；Shield 资料回答 Arduino D 引脚对应的外设连接。只有三者与 CubeMX 配置一致，候选 pinmap 才能进入到货复核。

## 3. Arduino 引脚到 MCU 复用的转换

Shield 写的 D7、D8、D14 等不是 MCU 端口名。规划先通过 NUCLEO 排针关系转换为 PA8、PA9、PB9，再由数据手册和 CubeMX 验证 AF。这个过程避免把其他开发板示例直接套到 F446RE。

## 4. 本轮候选 pinmap

- RS485：PA8 DE、PA9 USART1_TX、PA10 USART1_RX。
- CAN：PB8 CAN1_RX、PB9 CAN1_TX。
- SPI：PA5/PA6/PA7，PB6 与 PC7 分别作为两个片选。
- ADXL345 中断候选：PB4 GPIO_EXTI4，上升沿；NVIC 留待后续设计。
- I2C：PB10/PB3 对应 I2C2。
- 调试：PA13/PA14 保留 SWD；PA2/PA3 保留 USART2 VCP 候选。

## 5. 三个真实冲突怎样解决

PB8/PB9 优先给 CAN1，因此 VEML7700 不使用默认 I2C1，而改用 I2C2。PA5 优先给 SPI1_SCK，因此板载 LD2 不再作为心跳灯。PB3 用作 I2C2_SDA 后不保留 JTDO/SWO，调试模式只启用 SWDIO/SWCLK。

## 6. 时钟树如何影响外设

CubeMX 用 HSI 经 PLL 生成 180 MHz HCLK，APB1 为 45 MHz，APB2 为 90 MHz，并启用 OverDrive。SPI1 在 APB2 上以 32 分频得到 2.8125 Mbit/s；CAN1 在 APB1 上使用预分频 6、BS1 12TQ、BS2 2TQ 得到 500 kbit/s。数字必须同时出现在 `.ioc`、生成初始化和构建产物中才算可追踪。

## 7. 生成代码与项目代码的边界

`Core/` 与 `Drivers/` 由 CubeMX/STM32CubeF4 产生；项目自有薄封装放在 `bsp/`，应用启动钩子放在 `app/`，显式构建清单放在 `cmake/firmware.cmake`。对生成文件的项目修改只进入 USER CODE 区，避免再生成时丢失。

## 8. startup、链接脚本与四类产物

startup 文件提供向量表和复位入口；链接脚本描述 Flash/RAM 布局。ELF 保存可执行结构与调试信息，HEX/BIN 用于后续烧录，MAP 用于追踪符号与内存布局。T04 同时生成四者，防止只编译不链接。

## 9. `PASS_CROSS_BUILD` 与 `PASS_HARDWARE`

交叉构建通过只说明 GNU Arm、CMake、startup、链接脚本、HAL/CMSIS 和项目源文件能够形成 ARM ELF。
只有真实板卡完成供电、下载、运行与通信检查后，才可能进入硬件通过状态。S1-T04 审核时尚未完成
后续双端同步；当前 `[038]` 已有 clean cross-build 证据，但硬件仍为 `NOT_RUN`。

## 10. 实际问题与后续消费

首次板卡加载出现 “Board Project Options” 窗口，它是在等待组件选择而非卡死；取消 LED/按钮 BSP 后继续。CubeMX 6.18.0-RC3 的 Windows CMake 生成还出现 `syscalls.c/sysmem.c` 路径重复，项目改用相对路径 CMake 与 `nosys.specs`。S2 将消费电气和到货门，S3 设计 FreeRTOS 并发，S4 实现传感器事务，S5/S6 分别冻结 Modbus 与 CAN 协议。
