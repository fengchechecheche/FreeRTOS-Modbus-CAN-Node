## 1. 本工作块解决什么问题

一个嵌入式项目很容易在计划阶段不断增加关键词：STM32、FreeRTOS、Modbus、CAN、MQTT、云平台、
电机控制、故障诊断。关键词越多不等于项目越强；如果职责、证据和停止边界不清楚，后续就无法判断
什么真正完成，也容易把采购、交叉编译或单帧通信误写成完整系统通过。

P5-S1-T01 不写固件，而是解决四个基础问题：

1. 项目五是否是独立项目，还是项目三仓库中的一个附属目录；
2. 项目三 Linux 网关和项目五 STM32 节点分别负责什么；
3. Modbus 地址、寄存器和数据语义由谁拥有；
4. 每项未来能力需要什么测试和证据，才能进入 README、作品集或简历。

本工作块形成三份相互配合的权威产物：

- `project_scope.md` 供人阅读，冻结项目范围和声明边界；
- `requirements_traceability.yaml` 供工具检查，映射需求、任务、验证层和未来证据；
- 本教程解释为什么这样设计，以及本次审计实际发现了什么。

## 2. 阅读前需要知道的术语和基础概念

### 2.1 项目范围与需求追踪

项目范围说明“做什么”和“不做什么”。需求追踪则给每项要求一个稳定 ID，并记录它来自哪里、由谁
负责、在哪个任务中实现、用哪一层测试证明。二者缺一不可：只有范围说明时难以自动检查遗漏；只有
需求表时又很难理解整体动机。

### 2.2 主站、从站与设备地址

Modbus RTU 使用请求—响应模型：主站发起请求，从站只响应属于自己的地址。项目三的 Linux/C++
网关是主站；项目五的 STM32 节点是从站。同一条 RS485 总线上，每个活动从站地址必须唯一。

地址只是设备身份的一部分。即使两个设备地址不同，如果寄存器含义不一致，主站仍不能正确解释数据。
因此“地址不冲突”和“寄存器语义兼容”必须分别审核。

### 2.3 RS485 与 Modbus RTU

RS485 是差分物理层，规定如何在线缆上传输电气信号；Modbus RTU 是运行在串行链路上的协议，规定
地址、功能码、数据和 CRC。一个产品只写“RS485”并不能证明它支持 Modbus RTU。

### 2.4 经典 CAN 与 CANopen

经典 CAN 控制器提供仲裁、帧校验、ACK 和错误处理，但不会自动定义温度、光照或健康状态放在哪个
CAN ID 和 payload 中。CANopen 是更高层协议。本项目只实现经典 CAN 自定义遥测合同，不能把它
描述为 CANopen。

### 2.5 验证层

- `PASS_HOST`：主机上的纯逻辑或模拟测试通过；
- `PASS_CROSS_BUILD`：F446RE 固件可以交叉编译，不证明板上运行；
- `READY_FOR_HARDWARE`：软件和测试向量已具备硬件接入条件；
- `PASS_HARDWARE`：指定板卡、固件和接线上的实物测试通过；
- `PASS_INTEGRATION`：与指定主站、USB-RS485 或 SocketCAN 对端联调通过。

这些状态不能相互替代。采购也不是上述任何 PASS 状态。

## 3. 硬件、协议和 RTOS 的工作原理

### 3.1 为什么把项目五从项目三中拆出

项目三原规划把 STM32/FreeRTOS 作为 Linux 网关的硬件增强。后来硬件范围扩展到 F446RE、三类
传感器、Modbus 从站和经典 CAN，已经形成独立的构建系统、任务模型、协议合同和硬件证据链。

如果继续放在项目三仓库中，会出现两个问题：

- 项目三的软件网关可能已通过，但 STM32 尚未到货；一个仓库状态无法准确表达两条轨道；
- 项目五需要 C11、CubeMX、HAL、FreeRTOS 和交叉编译，而项目三使用 Linux/C++、CMake、MQTT
  和 systemd；二者的工具链、测试和 Release 条件不同。

因此项目五被定义为独立固件项目。项目三仍可在集成阶段轮询项目五，但不拥有项目五的内部实现，
也不能用自己的 PTY 或 MQTT 测试替代项目五硬件证据。

### 3.2 FreeRTOS 在项目中的作用

FreeRTOS 用于将采集、协议发布和健康监测拆成有界任务。这里的重点不是“创建很多任务”，而是明确：

- 哪个任务拥有外设或共享数据；
- 中断做什么、任务做什么；
- 队列、栈和缓冲区最大占用是多少；
- 某条总线故障时，其他任务是否还能继续运行；
- 如何观察任务栈、队列水位、错误和复位原因。

这些数值和实现要到 S3 通过代码与测试冻结。T01 只冻结必须回答的问题。

### 3.3 传感数据为什么需要质量和新鲜度

传感器断线后，内存里可能仍保留上一次有效数值。如果只发布数值，接收方会误以为它是新测量。
因此统一样本除了数值，还必须包含时间戳、序列号、质量、新鲜度和来源。Modbus 和 CAN 都应从同一
不可变快照生成，避免同一时刻的两个接口给出互相矛盾的状态。

## 4. 本项目中的数据流、任务和中断角色

候选数据流如下：

```text
BME280(SPI) ─┐
ADXL345(SPI) ─┼─> 驱动/ISR/DMA ─> 采集任务 ─> 不可变样本快照
VEML7700(I2C) ┘                                  │
                                                  ├─> Modbus 从站任务 ─> RS485
                                                  ├─> CAN 发布任务 ───> CAN
                                                  └─> 健康任务 ───────> 诊断/看门狗
```

T01 冻结的角色原则为：

- BME280 与 ADXL345 共享 SPI 数据线但使用独立片选；
- ISR 只清标志、记录时间戳或通知任务；
- 采集任务产生统一快照；
- Modbus 与 CAN 只消费快照，不反向拥有传感器；
- 健康任务观察质量、超时、队列和复位原因；
- RS485 或 CAN 故障不得停止采集与健康监测。

任务数量、优先级、周期、DMA 通道、队列深度和引脚仍是后续合同，当前不能写成已经配置。

## 5. 关键接口、配置和执行过程

### 5.1 已冻结的协议入口

项目五的 Modbus 候选入口已经冻结为：

```text
角色：RTU 从站
默认地址：4
默认串口：19200 8E1
功能码：0x03、0x04、0x06
异常响应：对应非法功能、地址、值和设备故障
```

地址 `4` 的选择不是随意增加数字。当前项目三冻结表已经使用：

- 地址 `1`：`environment_sensor`；
- 地址 `2`：`motor_actuator`；
- 地址 `3`：`fault_injection_device`。

项目五不实现电机，因此不能为了沿用旧计划中的地址 `2` 而假装符合 `motor_actuator` 语义。地址
`4` 当前未被该表占用，可以保留项目三现有合同，同时给项目五建立自己的寄存器表。

### 5.2 寄存器合同如何推进

T01 只冻结所有权，不冻结具体地址。P5-S5-T01 将根据真实样本 schema 定义：

- BME280 温度、湿度和气压；
- VEML7700 光照度；
- ADXL345 三轴加速度及经批准的受限特征；
- 时间戳或年龄、序列号、质量和健康状态；
- 只允许 `0x06` 写入的受限配置。

项目三在 P5-S5-T05 联调前需要单独的受控变更，把地址 `4` 加入主站配置和公开投影。本 T01 没有
权限修改项目三。

### 5.3 从范围合同到后续实现

推进顺序为：

1. T01 冻结项目范围和需求 ID；
2. T02 冻结硬件到货、安全和官方资料；
3. T03 获得授权后建仓并建立构建/主机测试骨架；
4. T04 建立候选 `.ioc`、最小固件和接口合同；
5. T05 冻结验收协议和证据 schema；
6. S2～S6 分别实现板级、RTOS、传感器、Modbus 和 CAN；
7. S7 只发布由最终 evidence matrix 支持的结论。

## 6. 为什么选择当前方案及没有选择的替代方案

### 6.1 独立仓库，而不是项目三子目录

独立仓库能让固件拥有独立工具链、版本、测试、Release 和失败状态。项目三只通过明确的 Modbus
合同消费项目五，不需要理解项目五内部的 FreeRTOS 任务和传感器驱动。

没有选择项目三 `firmware/` 子目录，是因为那会模糊 Linux 软件 PASS 与 MCU 硬件 PASS，并让
两个不同工具链共享一个发布状态。

### 6.2 地址 4，而不是地址 2

地址 `2` 已被项目三冻结为电机执行器。修改它会影响现有配置、黄金数据和测试。选择地址 `4` 可以
保留地址 `1`～`3`，并让项目五按真实状态监测节点语义设计寄存器。

没有选择“继续用地址 2，再把字段解释成传感器”，因为这会把温度、光照或振动伪装成转速、电流，
属于数据语义错误。

### 6.3 FreeRTOS 单主线，而不是双 RTOS

项目目标是展示有界并发和可靠协议实现，不是比较 RTOS。双主线会把有限时间消耗在重复移植、维护
和教程同步上。RT-Thread 只能作为 Release 后的独立对比，不进入秋招 MVP。

### 6.4 经典 CAN 自定义合同，而不是 CANopen

经典 CAN 已足以展示 bxCAN、过滤、中断、发送队列、错误恢复和 SocketCAN 联调。CANopen 会引入
对象字典、NMT、PDO/SDO 等大量额外合同，超出当前岗位证据所需范围。

## 7. 测试方法、证据和判定门限

T01 的验收对象是文档合同，而不是固件。候选检查包括：

- `project_scope.md` 章节完整，项目职责、MVP、非目标和状态词清楚；
- `requirements_traceability.yaml` 可解析，需求 ID 唯一；
- 每项 MVP 至少映射一个后续任务、一个验证层和一种未来证据；
- MCU 只使用 F446RE，G071RB 只出现在历史拒绝说明中；
- Modbus 地址在三份产物中一致为 `4`；
- 项目三地址 `1`～`3` 没有被静默改写；
- 光照和振动没有复用压力、转速或电流字段；
- 所有工程需求初始状态只使用 `planned`，许可证待决项使用 `blocked`；
- 没有把采购、主机测试或交叉编译写成硬件 PASS；
- 没有合并冲突标记、重复 ID 或未解释的任务 ID。

用户内容审核是 T01 的最后一道门。自动检查通过只说明结构和一致性满足候选要求，不能代替用户对
项目定位、范围和公开边界的确认。

## 8. 实际遇到的问题、根因、修复和回归证据

### 8.1 项目身份与总规划不一致

现象：总规划 v2 只列出三个独立项目，并把 STM32/FreeRTOS 作为项目三硬件增强；项目五新规划则
要求独立仓库和 Release。

根因：硬件增强后来扩展为完整的 F446RE、三传感器、Modbus 从站和 CAN 节点，但总规划 v2 尚未
同步这一拆分。

本次处理：D01 明确项目五是从项目三硬件增强中拆出的独立固件项目，项目三只保留 Linux 主站与
网关职责。总规划 v2 的正文更新不在 T01 授权范围，留待单独审核。

回归依据：`project_scope.md` 的跨项目责任矩阵和 `P5-SYS-001` 均要求两个项目分别验收。

### 8.2 Modbus 地址 2 冲突

现象：项目五原计划写默认地址 `2`，但项目三冻结的 `register_map.yaml` 已把地址 `2` 分配给
`motor_actuator`。

根因：项目五沿用了项目三早期硬件台架文档中的“STM32 地址 2”，没有同时核对后续冻结的设备表。

本次处理：D02 将项目五默认地址改为 `4`，保留项目三地址 `1`～`3`。D03 规定项目五独立维护
寄存器合同。

回归依据：`requirements_traceability.yaml` 中 `D02_modbus_default_slave_id`、
`P5-MODBUS-001`、`P5-MODBUS-005` 和 `P5-MODBUS-006` 共同约束地址与所有权。

### 8.3 传感器语义无法直接复用项目三寄存器表

现象：项目三的环境设备没有光照和加速度；地址 `2` 是电机转速、电流和故障字段。

根因：项目三寄存器表最初服务 PTY 网关测试，并不是为当前项目五三传感器节点设计。

本次处理：禁止把光照写入压力字段、把振动写入转速或电流字段。具体项目五寄存器地址延后到
P5-S5-T01 根据统一样本模型冻结。

回归依据：`P5-SENS-004`、`P5-MODBUS-005` 和范围合同的变更控制共同防止语义偷换。

### 8.4 F446RE 与旧 G071RB 文本混存

现象：项目三采购文档顶部已更新为 F446RE，但后半部仍保留 G071RB、旧收发器和 STM32CubeG0
链接。

根因：采购选型发生受控变化后，原文档没有完成全篇同步。

本次处理：项目五只接受 F446RE，G071RB 仅作为历史拒绝关键词。引脚、`.ioc` 和 BSP 必须由
F446RE、Shield 官方资料和到货实物重新冻结。

回归依据：`P5-SYS-002` 要求合同、交叉编译和硬件三层共同验证，不能只靠采购表顶部文字。
