# P5-S3-T05 看门狗、健康监测与故障恢复

## 目标与边界

本任务建立健康状态机、喂狗决策、恢复升级和复位原因编码。当前没有开发板，因此只验证纯逻辑和
ARM 编译链接，不启动真实 IWDG，也不声称复位记录能够跨复位或断电保存。

## 关键设计与实施

`health_task` 每秒比较其他四个任务的 release counter。第一次只保存基线；某个任务一次没有前进时
进入 `DEGRADED`，连续两次才进入 `RESET_REQUIRED`。health task 不检查自己的“下一次心跳”，因为
只有它能产生 feed decision：它若卡住，系统自然不会得到下一次允许喂狗的决定。

deadline miss、budget overrun、queue drop/full、snapshot contention 和 RS485 error 都按增量观察。只要
任务仍在前进，这些瞬态问题只触发降级或 owner-local recovery，不直接复位整机。恢复每个 episode
最多失败三次；health 只做决策，不越权调用 SPI、I²C、RS485 或 CAN HAL reset。

健康状态变化使用 T04 的 12 B 值对象进入静态诊断队列。正常每秒不写日志，初次进入健康状态也不
制造事件。queue 自身满时仍采用 drop-new，并且事件能否入队不会反过来改变健康结论。

固件会读取并清除 RCC reset flags，保存当前启动的 raw flags 与归一化原因。纯逻辑 reset record 包含
magic、版本、长度、boot count、连续恢复复位数、最后原因/故障和 checksum；三次连续恢复复位会在
策略中 latch。当前没有选择 `.noinit` 或 backup-domain 后端，所以 record persistence 仍是 `NOT_RUN`。

## 验证结果

- Host Debug/Release：均为 9/9；
- one/two-epoch stall、warning storm、recovery success/failure、counter saturation 和 reset-loop latch：PASS；
- 单一、多重和未知 reset reason、record corruption 与 stable-clear：PASS；
- ARM Debug/Release：构建链接 PASS；
- Debug/Release RAM：9448 B / 9440 B，静态资源门 PASS；
- 静态负向测试能拒绝一次 stall 立即复位、错误 recovery budget、默认 IWDG、task delete 和第二喂狗路径。

这些结果不代表 IWDG 已刷新/超时，也不代表真实 task stall、queue watermark、mutex contention 或
复位保存已经通过硬件验证。

## 实际问题与修复

reset codec 最初即使加入 firmware source，也可能因为 `--gc-sections` 且没有目标端调用而被链接器
移除。实施中将 current-boot RCC flag capture 接入 RTOS 初始化，使
`app_reset_reason_decode` 真正进入最终 ELF；同时没有把尚未验证的 reset record 持久化伪装成已接入。

Windows 当前终端仍不提供项目所需的 CMake/Python 入口，因此全部 Host、ARM 和静态检查继续在
`Ubuntu-24.04-STM32` 工具链中执行。
