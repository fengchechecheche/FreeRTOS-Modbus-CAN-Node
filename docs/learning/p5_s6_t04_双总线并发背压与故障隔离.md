## 1. 目标与边界

本任务验证 RS485/Modbus 与 CAN 同时运行时，一条链路的拥塞或故障不会扩散到另一条链路、采集任务和健康任务。硬件尚未到货，因此本轮使用虚拟时间完成软件合同验证，不声称真实吞吐、恢复耗时、deadline 或物理断线已经通过。

本任务没有增加第六个任务、RTOS 队列、互斥量、动态内存或生产级“双总线模拟器”，也没有修改 CubeMX、协议 map 和固件 runtime。

## 2. 为什么复用生产模块

如果测试重新实现一套 RS485/CAN 状态机，测试通过只能证明模拟器自洽。当前矩阵直接链接：

- Modbus RTU ADU、CRC 和 stream parser；
- RS485 固定缓冲区半双工状态机；
- CAN latest-wins、事件 FIFO、公平发送和 bus-off 恢复控制器；
- 五任务时间合同、诊断 admission 和健康策略。

Host 文件只提供虚拟时钟、假 UART/CAN 操作和固定输入，因此测试结论仍对应生产模块的真实分支。

## 3. 背压设计

普通遥测采用 latest-wins。消费者变慢时保留最新值而不是无限排队，旧值被替换时增加计数。BME 的两帧必须保持同一 sequence；primary 已经提交后，不能用新一代 secondary 拼接。

状态事件使用深度 8 的 FIFO，相同 source/code 可以合并。故意压满时允许拒绝新事件，但必须增加 drop 计数。诊断队列也使用零等待入队和显式 drop。这里的验收目标是“不可静默”，不是在极端注入下苛求零丢失。

RS485 正在发送时，第二次发送返回 `BUSY`，不能覆盖当前固定缓冲区。CAN HAL 返回 busy 时，当前队头和 token 保持不变，等待下一次有界 service。

## 4. D01～D08 结果

| 场景 | 关键结果 |
|---|---|
| D01 正常并发 | 2 个 Modbus 帧、2 个 CAN 提交，五任务模型均前进 2 次 |
| D02 慢主站 | 请求间空闲不报错；1 次 t1.5 违规被分类；下一帧恢复 |
| D03 CRC 错 | 1 次 CRC mismatch，坏帧不交付，下一合法帧通过 |
| D04 RS485 忙/超时 | 第二发送返回 BUSY，8 字节帧虚拟 timeout 为 25 ms，RX 恢复 |
| D05 CAN 慢消费者 | latest-wins 替换 1 次，HAL busy 1 次，队头不变 |
| D06 队列满 | CAN/诊断各 1 次显式 drop；11 帧有界提交；health 和 BME pair 未饿死 |
| D07 CAN 断开 | 1 s 虚拟等待、3 次失败后 latched；Modbus、采集和 health 继续前进 |
| D08 同时故障 | CRC、RS485 timeout、CAN bus-off 都保留分类；两条链路可分别恢复 |

## 5. 实际问题与修复

写入较大的 Host 源文件时，Windows 单条命令达到长度上限。处理方式是先用补丁工具生成受控临时文件，再复制到 WSL 权威仓库；没有通过脚本拼接或修改 Git 状态。该问题与固件逻辑无关。

新增测试首次编译和执行即通过严格 `-Wall -Wextra -Wpedantic -Werror`。本轮没有发现需要修改生产 runtime 的缺陷。

## 7. 限制与下一步

Host 虚拟 tick 不能转换为真实毫秒测量，task model 的 release 计数也不能替代 MCU 调度观测。硬件到货后，只需做短时双链路并发、一次 RS485 断开、一次 CAN 对端断开和恢复；真实恢复时间、deadline miss、stack watermark 与吞吐在实物阶段记录。
