# P5-S5-T05｜项目三联调与主从站证据

## 1. 为什么先做独立主站

项目五是 Modbus RTU 从站，项目三是 Linux Modbus 主站。若一开始就把二者直接连接，失败可能来自 STM32 固件、RS485 接线、USB 适配器、项目三 profile、调度器或数据投影，排查范围过大。

T05 先用一个功能单一的 HIL 探针检查地址、功能码、CRC 和静默语义。独立链路通过后，项目三联调只需关注 profile、调度、质量状态和上层投影。

```text
P5 Host/ARM candidate
        |
        v
independent USB-RS485 PASS_HARDWARE
        |
        v
Project Three profile PASS_SOFTWARE
        |
        v
real P5/P3 PASS_INTEGRATION
```

三层结果不能互相替代。

## 2. 当前为什么仍是无硬件候选

本轮只运行：

```bash
python3 tools/modbus_hil_probe.py --self-test
python3 tools/modbus_hil_probe.py --dry-run
```

两条命令都输出 `serial NOT_OPENED`。它们证明固定帧和响应判定工具可以运行，不证明 PA9/PA10、DE、Shield、A/B/GND、USB-RS485 或外部主站已经工作。

因此当前状态是：

```text
software readiness = READY_FOR_HARDWARE
physical RS485      = WAITING_FOR_HARDWARE
Project Three       = NOT_RUN
```

## 3. 探针如何限制风险

探针遵守四条规则：

1. 不自动扫描端口，必须显式传入 `--port`；
2. 默认只读，地址迁移必须增加 `--allow-address-write`；
3. 写地址还要明确确认默认地址 4；
4. 任一迁移失败立即停止，不反复盲写。

这种设计避免脚本误连其他串口设备，也避免一次失败后不知道从站当前处于地址 4 还是 5。

## 4. 为什么静默也是结果

坏 CRC、广播地址 0 和非本机地址不应收到响应。普通串口工具常把“没有响应”统一显示成 timeout，但 T05 必须结合测试意图解释：

- 正常读请求没有响应：失败；
- 明确的静默用例没有响应：通过；
- 静默用例收到任意字节：失败。

因此 HIL 探针为每个 case 保存 `normal`、`exception` 或 `silence` 预期，而不是把所有 timeout 视为同一种错误。

## 5. 最大响应为何单独测试

完整 input image 是 122 个寄存器：

```text
address + function + byte_count + data + CRC
= 1 + 1 + 1 + 244 + 2
= 249 bytes
```

短响应通过不能证明 DMA、stream buffer、caller-copy TX 和 DE 时序能处理 249 B。因此 H03 在真实台架上必须执行一次完整读取，但不要求大量重复或长稳。

## 6. 地址写入为何延迟生效

`0x06` 正常响应必须 echo 原请求。如果从站在开始发送前立即改地址，响应可能使用新地址，主站却仍在等待旧地址的 echo。

项目五先把新地址放入 pending，只有 echo 的最终 TX complete 才提交。H08/H09 用 4→5→4 验证：

1. 写请求的 echo 使用旧地址；
2. TX complete 后旧地址静默；
3. 新地址可以读取；
4. 最终恢复地址 4。

复位后回到 4 是易失配置合同，不代表 Flash 持久化。

## 7. 项目三 profile 为什么不能复用地址 2

项目三已有：

- 地址 1：`environment_sensor`；
- 地址 2：`motor_actuator`；
- 地址 3：`fault_injection_device`。

项目五冻结为地址 4，并拥有独立的传感器、质量、新鲜度和健康语义。若复用地址 2 或 `motor_actuator` 字段，虽然帧可能收发成功，数据含义却是错误的。

后续 profile 应使用独立名称，例如 `stm32_sensor_node`，稳态只读 `0x03/0x04`。维护地址的 `0x06` 不进入正常轮询。

## 8. 本轮遇到的问题与修正

### 8.1 新文件补丁行数声明错误

首次写入探针时，统一补丁声明 423 行，但实际内容为 516 行，导致 Python 文件在 `address_write_cases()` 中间被截断。语法检查立即报告括号未闭合。

修正方法是先用原补丁精确回退这个未完成的新文件，再修正行数声明并完整重放。没有用覆盖命令修改其他文件，也没有留下 `.orig`/`.rej`。

### 8.2 self-test 不应隐式加载串口依赖

若在模块顶层导入 pyserial，无硬件开发环境会因为依赖缺失而无法验证 CRC 和固定帧。最终把 import 放在 `--port` 路径中，使 self-test/dry-run 只依赖 Python 标准库。

### 8.3 写配置需要双重显式确认

仅有 `--allow-address-write` 容易在错误的起始地址状态下执行。最终增加 `--confirm-default-address 4`，并拒绝在 self-test/dry-run 中使用写入参数。

## 9. 到货后的最短路径

1. 完成 S2 到货、安全、ST-LINK 和最小固件门；
2. 使用短线共地 USB-RS485，只运行一个主站；
3. 先做 H01～H07，只读和静默通过后再做地址写；
4. H08/H09 完成后确认地址 4；
5. 人工执行复位和一次断开/重连；
6. 独立 `PASS_HARDWARE` 后，再审核项目三地址 4 profile。

正常成功只保存简洁结果表。失败时保留一条有定位价值的帧和恢复结果即可。
