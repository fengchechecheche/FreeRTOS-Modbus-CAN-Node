# P5-S3-T04 队列、互斥与数据所有权

## 目标与边界

本任务解决三个问题：事件怎样有界排队、共享快照怎样一致复制、共享总线由谁访问。它不实现传感器
数据结构、Modbus 命令或 CAN 报文，也不改写 T03 已完成的中断通知链路。

## 关键设计与实施

不同数据选择不同 FreeRTOS 原语：中断只需唤醒 `protocol_task`，继续使用 task notification；需要
保留有限顺序的诊断事件使用静态 queue；多个任务只需读取最新状态时使用 snapshot，而不是累积历史
样本；未来 Modbus 写命令需要独立 command queue，但必须等 S5 明确命令语义后再创建。

诊断事件是 12 B 的值对象，由时间戳、附加值、来源和代码组成，不含指针。queue 深度为 8，producer
等待时间为 0；满时丢弃新事件并递增饱和计数器。`diagnostic_task` 每个 200 ms 周期最多取出 2 项，
因此慢消费者不会让高优先级 producer 阻塞，也不会让一次诊断周期无限延长。

系统快照只在复制期间持有一个静态 mutex。reader 复制到自己的 local buffer 后立即解锁，再执行
编码、发送或诊断；writer 也只复制完整值。锁竞争时函数显式失败并计数，不等待到
`portMAX_DELAY`。SPI1/I²C2 不使用该 mutex，运行期只允许 `acquisition_task` 访问总线。

## 验证结果

- Host Debug/Release 均为 8/8；
- burst 12/depth 8 得到 8 个 accepted 和 4 个 drop-new；
- FIFO、值复制、慢消费者、每周期最多 drain 2、无效输入、计数器饱和和时间戳回绕均通过；
- ARM Debug/Release 均成功构建链接；
- Debug/Release 静态 RAM 分别为 9216 B 和 9208 B，资源门通过；
- 静态合同能拒绝 depth 0、动态 queue、阻塞等待和 callback 中普通 queue API。

上述结果不等于板上 queue/mutex 压力测试通过。当前运行时状态仍为 `NOT_RUN`，硬件状态仍为
`WAITING_FOR_HARDWARE`。

## 实际问题与修复

当前 Windows 终端没有可用的 CMake/Python 执行入口，因此验证改由 `Ubuntu-24.04-STM32` 中既有的
CMake、GCC、GNU Arm Embedded GCC 和 Python 完成。源码仍保持同一工作区内容，未增加第二套构建
合同。本轮没有发现需要修改设计的 queue、mutex 或所有权缺陷。
