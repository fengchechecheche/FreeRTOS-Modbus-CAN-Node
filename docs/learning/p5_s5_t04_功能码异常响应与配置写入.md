# P5-S5-T04 功能码、异常响应与配置写入

## 1. 目标与边界

本任务把 T03 输出的 CRC-valid Modbus RTU ADU 接到真实从站功能处理器，实现地址 4 下的
`0x03`、`0x04`、`0x06`、异常响应和易失地址写入。

无硬件阶段只证明 Host 行为、ARM 编译链接和静态资源边界。NUCLEO-F446RE、RS485 收发器、
249 B 实际应答、DE 波形和项目三联调仍为 `WAITING_FOR_HARDWARE / NOT_RUN`。

## 2. 为什么功能处理器保持纯 C

功能处理器只接收已经验证 CRC 的 ADU view，并通过两个回调取得 input image、发送 response。
它不包含 HAL、FreeRTOS、DMA 或 GPIO。这样可以在 Host 上直接验证每一种请求和异常，不需要
为每个用例模拟 UART 中断。

状态只包括：

- active slave address；
- configuration generation；
- 一个 pending address；
- 聚合诊断计数；
- 调用方提供的固定 response/image buffer。

没有动态分配，也没有保存原始帧历史。

## 3. 功能码和异常判定顺序

先处理地址：广播 0 和非本机地址都静默忽略。只有当前地址才进入功能码处理。

`0x03` 和 `0x04` 的数据必须恰好为起始地址与数量四个字节。数量为 0 或大于 125 返回
exception `03`；数量合法但范围越界返回 `02`。`0x04` 每次请求只生成一次 122-register
request-local image，provider 失败返回 `04`。

`0x06` 只允许写 holding 0。写其他地址返回 `02`，值不在 1～247 返回 `03`。未实现功能码
返回 `01`。异常响应为 `function | 0x80`、一个异常码和 CRC。

## 4. 为什么地址不能立即生效

如果解析 `0x06` 后立即把地址从 4 改成 7，应答可能会使用新地址 7，原主站会把它视为错误
或超时。因此采用两阶段提交：

```text
请求校验 -> 使用旧地址生成 echo -> BSP 接受发送 -> pending=7
最终 USART TC -> active=7 -> configuration_generation++
```

TX 拒绝不会产生 pending；UART error、timeout、recovery failure 或 RX/TX 冲突会取消 pending。
写入相同地址仍正常 echo，但 generation 不增加。该设置不写 Flash，复位后恢复 4。

## 5. 一次加锁的快照

若分别调用 measurement、monitor 和 health getter，它们会分别加锁，三份数据可能来自不同发布
时刻。T04 增加 aggregate getter，在既有 mutex 下完成一次投影复制，然后立即解锁。

锁外才执行：

- measurement age/state 刷新；
- stale mask 重算；
- 122-register 映射；
- 32 位 high-word-first 拆分；
- CRC 和发送。

mutex 仍为 zero-wait。无法立即取得时返回 unavailable，由协议层产生 exception `04`，不会扩大
锁等待或阻塞 acquisition task。

## 6. Register image 编码

image 包含 18 个 header register、17 个 32 位测量值、四组 metadata、monitor/fault/recovery
摘要和 health/RS485 聚合。映射前整体清零，所以从未获得 last-good 的值没有伪造工程意义。

有 last-good 但已 stale/offline 时保留数值，同时通过 state、value_present、value_retained、age
和 quality 解释。measurement state、sensor fault 与 health state 都使用显式 `switch` 转换，
不能依赖 C enum 的当前数值或 struct 内存布局。

## 7. 验证与资源

新增两项 Host 目标：

- `p5.host.modbus_server`：正常请求、异常、静默、最大应答和延迟提交；
- `p5.host.modbus_register_image`：全部地址、signed/unsigned、word order、缺失/retained 和 wire code。

它们与既有 16 项一起在 Debug/Release 运行。固件继续使用五个 256-word task stack、一个既有
snapshot mutex 和一个既有诊断 queue；没有增加 task、queue、mutex、heap 或 stack。

## 8. 实际问题与修复

1. BSP 在同一 mailbox snapshot 同时出现 RX frame 和 TX complete 时会按 direction conflict 进入
   I/O recovery，但返回的 mask 不一定包含 UART-error bit。应用层因此同时检查这两个事件，避免
   错把冲突当成成功 TX complete 并提交地址。
2. measurement getter 会在请求时刷新 stale 状态，而 monitor 中保存的 stale mask 可能来自上一次
   acquisition 发布。Modbus 投影在解锁后依据刷新后的四份 metadata 重算 mask，保证同一 response
   的 header 与 metadata 一致。
3. legacy ASCII smoke 与默认 Modbus transport 必须互斥。link-failure 回调放在编译期开关的
   Modbus 分支，避免 legacy 配置重新引用完整 server/image 路径。
