## 1. 为什么证据矩阵不能只有一个 PASS

本项目已经有 Host 测试、ARM 交叉构建、vcan、dry-run 和 clean replay，但还没有板卡、传感器、
USB-RS485、项目三、candleLight 或长稳实物结果。把这些内容合并成“项目通过”会丢失最重要的环境边界。

本轮把每项能力拆成“执行层级 + 结果”。例如：

```text
CAN software = PASS / HOST
SocketCAN    = PASS / VIRTUAL_BUS
physical CAN = NOT_RUN / HARDWARE
```

这样既能展示已完成的软件工作，也能在排障时直接知道缺少的是哪一层。

## 2. 提交和固件身份怎样绑定

矩阵本身以 `[037]` 为基线，因为该提交收录了 T02 工具和报告；真正执行 clean build 的源码是
`[036]`。两者分开记录，不能把 `[037]` 写成已经重新烧录。

每行有 `evidence_commit`；被 T02 clean replay 覆盖的软件行还可以有 `regression_anchor=[036]`。
只有证据实际消费了某个二进制时才填写 `firmware_sha256`。当前硬件行全部 `NOT_RUN`，因此固件哈希
必须为 null，避免把“准备烧录的候选”误写成“已经烧录的固件”。

## 3. 24 行为什么足够

矩阵没有逐测试、逐帧或逐日志展开，而是保留 24 个排障入口：

- 环境/Release 4 行；
- Host 与 ARM 3 行；
- BSP、三传感器、watchdog 6 行；
- RS485、PTY、项目三 4 行；
- CAN、vcan、双总线 5 行；
- soak 2 行。

软件和硬件分行后，即使设备到货，也只需更新真正执行过的行，不需要重做整套 Schema。

## 4. 最容易混淆的四组结论

### 4.1 dry-run 与 PTY

Modbus probe 的 self-test/dry-run 没有打开串口，因此它们仍不能算 PTY 证据。后续 `[042]` 使用 Linux
PTY 把同一 probe 接到项目真实 C 语言 RTU stream/server/register image，H01～H07 共 10 个用例通过，
最大响应 249 B。该结果只提升 `RS485-02 / HOST`，不证明 USB-RS485 或项目三联调。

### 4.2 vcan 与物理 CAN

vcan 和 can-utils smoke 验证 Linux SocketCAN 工具链与帧格式，不证明 candleLight、终端、ACK 或 MCU
接收。CAN 矩阵保留一个虚拟 PASS 和一个物理 NOT_RUN。

### 4.3 Host 双总线与实物并发

D01-D08 验证固定软件状态机在虚拟 tick 下的背压和隔离。它不证明真实调度延迟、吞吐或电气故障恢复。

### 4.4 clean replay 与 bit-for-bit

`[036]` 可以从零完成构建，但 FreeRTOS `__FILE__` 绝对路径使两个目录的 Release BIN/HEX 不同。
所以 procedural replay 为 PASS，bit-for-bit 保持 NOT_CLAIMED。

## 5. checker 只检查什么

`tools/check_evidence_matrix.py` 是轻量结构检查器。它检查：

- 最多 24 行、ID 唯一和枚举合法；
- evidence commit 和 SHA-256 格式；
- 配置/证据路径存在且是公开相对路径；
- 硬件 PASS 必须有实际固件和去标识化硬件身份；
- NOT_RUN 不能携带“已烧录”固件哈希；
- summary 与实际行数一致；
- 公共 JSON 不含用户目录和高置信隐私模式。

它不读取全部历史 Markdown 自动判断 PASS，也不生成原始日志、数据库或网页仪表盘。

## 6. 公开与本地证据如何分开

公开层只有 compact JSON 和本 Markdown 视图，引用已经存在的报告。

本地层只建立一个被忽略的索引，指向 T02 已存在的有界 raw command summary。因为硬件没有执行，
本地索引不生成板卡、RS485、CAN 或长稳占位文件。未来只有出现值得跨会话排查的问题，才按冻结的
diagnostic record 协议增加一条记录。
