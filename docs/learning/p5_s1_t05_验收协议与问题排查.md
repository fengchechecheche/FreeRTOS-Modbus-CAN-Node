# P5-S1-T05 轻量验收协议与问题排查

## 1. 目标与边界

T05 的目标不是搭建完整测试数据平台，而是建立一套不会拖慢开发的问题记录方法。后续正常成功检查
只需留下简短结论；真正阻塞推进、需要跨会话排查或必须回归的问题，才使用结构化诊断记录。

这项工作不执行硬件测试、RS485/CAN 联调、长稳或清洁复现，也不为最终项目展示提前制造数据。

## 2. 关键设计与实施

### 2.1 为什么取消五文件证据包

原设计要求每次运行生成 manifest、config、events、summary 和 failures。它适合多人协作、自动化测试
平台或合规审计，但本项目当前由个人分阶段推进。大量固定字段和逐事件记录会增加维护负担，真正发生
问题时反而难以找到关键线索。

修订后只有一个 `diagnostic_record.schema.json`。它的 11 个必需字段只回答：问题属于哪个任务和
范围、发生在哪个环境和提交、看到了什么、下一步做什么。固件哈希、接线、对端配置、错误片段、根因、
修复和回归结果只在相关时填写。

### 2.2 什么时候值得记录

值得建立诊断 JSON 的问题需要至少满足一项：阻塞后续任务、需要跨会话继续、修复后必须回归，或问题
依赖硬件/总线配置。立即修正的命令错误、无影响的警告、重复成功构建和无异常事件不进入诊断目录。

### 2.3 状态为什么仍然保留

`PASS_HOST`、`PASS_CROSS_BUILD`、`PASS_HARDWARE` 和 `PASS_INTEGRATION` 仍然有价值，因为它们防止
把主机测试或编译成功写成实物通信成功。但这些状态只需人工在任务验证记录中使用，不需要复杂程序
自动推导。

### 2.4 数据如何最小化

真实诊断记录默认进入 `.private/diagnostics/`。原始日志、抓包和照片只有在能够帮助定位问题时才作为
附件保存；公开仓库只放协议、Schema 和去标识化合成示例。S7 如需展示材料，再从已审核结果中选择。

## 3. 验证结果

- Schema 使用 JSON Schema Draft 2020-12；
- 必需字段为 11 个，其余均可选；
- 合成失败示例和修复回归示例均通过 Ubuntu 现有 `jsonschema 4.10.3` 验证；
- 七阶段任务文件中共提取 35 个唯一任务，S1～S7 各五项；
- 教程索引只登记任务、标题、文件名和状态，不生成尚未实施的正文。

T05 已于 2026-08-14 完成用户内容审核并正式通过。该通过只证明轻量协议可以供后续任务使用，
不证明任何后续硬件或总线测试已经执行。

## 4. 实际问题与修复

### 问题：初版证据合同超出项目实际需要

初版把故障排查、全过程审计和最终项目展示合并为一个证据系统，要求每次运行生成五类文件和完整环境
信息。用户指出这会产生大量可能永远不会使用的数据，并影响项目按时推进。

根因是没有把“日常开发排查”和“S7 最终展示”拆开。修订后，日常开发采用成功摘要和按需诊断记录；
展示材料推迟到 S7 从已有审核结果中提取。两个合成示例验证了轻量 Schema 能表达阻塞问题和回归通过，
不需要为普通成功运行生成额外证据包。

本轮命令引号等立即修正的临时操作问题没有影响工程结果，按照新协议不建立诊断记录。

## 5. 限制与下一步

轻量 Schema 不尝试自动计算状态，也不覆盖所有未来故障类型。若后续真实问题发现缺少必要字段，可在
对应任务中把字段添加为可选项并记录版本；不得因为“将来可能有用”提前扩展。

下一步由 S2 消费板级最低验收和按需诊断规则。硬件仍处于 `WAITING_FOR_HARDWARE`，T05 不自动开始
接线、烧录或实物测试。
