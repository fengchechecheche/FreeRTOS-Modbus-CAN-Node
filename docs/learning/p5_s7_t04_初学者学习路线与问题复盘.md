> 路线基线：`[038] a8950b5d506d4b02b65c72aa1ec4d7fc6b85da9b`

## 1. 本工作块解决什么问题

项目已经有大量按任务形成的教程，但“文件很多”不等于初学者知道先学什么，也不等于文档与当前代码
一致。T04 建立一条 S1→S7 的权威阅读顺序，恢复四份已经审核却未同步的 S1 教程，并把真实问题集中
成一个有界台账。

本轮不新增固件功能，不补做硬件，也不把 34 份可用教程写成 35 份全部完成。T05 只有规划条目，没有
空壳文件。

## 2. 路线为什么按 S1→S7

路线遵循“先边界和工具、再板级与 RTOS、再数据、再协议、最后 Release”的依赖关系：

```text
S1 范围/仓库/安全
 └─> S2 BSP/总线
      └─> S3 RTOS/资源/中断
           └─> S4 传感器/数据模型
                └─> S5 Modbus/RS485
                     └─> S6 CAN/双总线/长稳方法
                          └─> S7 许可/复现/证据/表达
```

初学者可以使用三条快速导航，但状态和文件映射仍只有一份，位于
[`README.md`](README.md) 和 [`index.md`](index.md)。

## 3. 35 项与 34 份文件

T04 A0 发现 index 虽然列出 35 项，独立仓库却只有 29 份任务教程。缺失的 S1-T01～T04 在规划仓库
已有用户审核正文，因此本轮以公开安全方式恢复；再加上当前 T04 教程后，共有 34 份。

S7-T05 尚未实施，保持：

```text
index status = PLANNED
file         = absent
release      = not authorized
```

这种表示比创建空文档更诚实，也能让检查器区分“路线预留”和“内容存在”。

## 4. 教程与当前代码怎样保持一致

逐字重写所有历史教程会抹掉任务当时的上下文，也容易把旧测试结果冒充当前重新执行。本轮只审查高漂移
锚点：CubeMX/CubeF4/FreeRTOS 版本、Modbus 地址和串口 profile、CAN bitrate/ID、当前 Host 回归规模和
evidence matrix 计数。

历史测试计数继续保留；只有教程把历史值说成“当前值”时才修订。四份恢复教程也明确区分规划侧来源、
任务实施时事实和 `[038]` 当前边界。

## 5. 为什么问题台账只保留 12 条

项目中发生过很多一次性操作问题，但初学者真正需要的是可迁移的错误模式：

- 证据系统设计过重；
- Windows/Linux 行尾和路径边界；
- CubeMX 广泛生成与严格 allowlist；
- FreeRTOS 中断优先级；
- 失败路径上界和资源统计语义；
- Release 测试断言、状态/新鲜度建模和头依赖；
- 运行时长门、公开路径、许可和可复现性边界。

[`problem_ledger.md`](problem_ledger.md) 为每条记录现象、错误假设、根因、处理、回归和预防。没有实际
执行的硬件路径仍留在 evidence matrix，不被包装成问题修复。

## 6. 一致性检查器

`tools/check_learning_docs.py` 使用 Python 标准库检查：

1. README/index 各有相同的 35 个唯一任务；
2. T04 候选时恰好 33 `FROZEN`、1 `READY_FOR_CONTENT_REVIEW`、1 `PLANNED`；
3. 只有 T05 可以 PLANNED 且没有文件；
4. 其余 34 份教程存在；
5. 版本、Modbus 和 CAN 锚点与仓库权威文件一致；
6. 问题台账最多 12 条且证据存在；
7. 路线和恢复教程不泄露本机用户路径；
8. 官方资料含发布方、HTTPS 链接和核验日期。

该检查器不尝试用正则理解全部技术自然语言，也不访问网络。官方链接的可达性在 T04 实施时单独只读
核验，后续 checker 只保护记录结构。

## 7. 一手资料选择

资料入口集中在学习 README，优先使用 ST、FreeRTOS、Modbus Organization、Bosch Sensortec、Vishay、
Analog Devices 和 Linux kernel 官方页面。can-utils/candleLight 上游仓库作为工具实现参考单列，不把
它们当作 CAN 协议标准。

官方手册说明器件和协议应该怎样工作；项目是否真的工作仍由 Host、cross-build、virtual bus 和硬件
证据分层决定。

## 8. 实际问题与处理

### 8.1 索引与文件数量不一致

现象是 index 声明 35 项，但仓库只有 29 份教程。根因不是教程未编写，而是早期四份已审核 S1 教程
留在规划产物目录，后来任务从 S1-T05 开始才稳定同步到独立仓库。本轮只恢复这四份审核正文，不复制
validation、计划稿或私有资料。

### 8.2 历史状态没有归一

S5-T05、S6-T01、S6-T03 已完成用户内容审核和后续提交，但 index 仍保留
`READY_FOR_CONTENT_REVIEW`；顶部还有 S5-T04 的旧临时说明。本轮按审核记录归一为 `FROZEN`，不改写
其工程执行层级。

### 8.3 恢复正文含本机身份和过时“当前”表述

S1-T03 原文记录了具体 Linux 用户 home，并把“尚无远程仓库”等 S1 时点事实写成当前状态。公开恢复
时删除本机身份，并把这些句子标为历史；没有用 `[038]` 冒充重新执行 S1。

## 9. 验证与限制

T04 不修改固件、CMake、`.ioc`、协议、驱动或测试，因此不重跑完整 Host/ARM。它复用 T02 clean replay
和 T03 evidence matrix，并运行 learning/evidence/release 三类文档检查及 replay runner self-test。

当前仍不能声称：

- 35 份教程全部完成；
- 板卡、传感器、RS485、项目三或物理 CAN 通过；
- 10 分钟、60 分钟或 8 小时硬件长稳完成；
- v0.1.0、tag、Release 或求职材料已经生成。
