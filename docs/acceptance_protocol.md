# 项目五轻量验收与问题诊断协议

> 版本：1.0.0  
> 冻结任务：P5-S1-T05  
> 状态：已审核冻结（P5-S1-T05 `PASS`）  
> 审核日期：2026-08-14  
> 原则：正常成功只留摘要；只有有助于问题定位和回归时才生成诊断记录

## 1. 目的

本协议用于帮助项目顺利推进和排查真实问题，不建立全面审计系统，也不要求为项目展示提前生产数据。
后续任务只记录足以回答以下问题的信息：

1. 检查了什么；
2. 结果是否满足当前任务；
3. 若失败，问题发生在哪里、实际看到什么、下一步怎样处理；
4. 修复后是否通过必要回归。

项目展示由 S7 从已经审核的验证记录中按需提取。日常成功运行不生成五文件证据包、逐事件日志或
无人消费的原始数据。

## 2. 状态边界

| 状态 | 允许结论 | 禁止外推 |
|---|---|---|
| `PASS_HOST` | 指定主机环境中的软件测试通过 | 不证明 ARM 固件或板上运行 |
| `PASS_CROSS_BUILD` | 指定提交的目标固件完成交叉编译和链接 | 不证明烧录、启动或通信 |
| `READY_FOR_HARDWARE` | 软件、固件和安全前置具备接入实物的条件 | 不等于实物已经可用 |
| `WAITING_FOR_HARDWARE` | 硬件轨道等待实物或实物确认 | 不否定已取得的软件结果 |
| `PASS_HARDWARE` | 指定板卡、固件和必要接线上的检查通过 | 不自动证明总线对端互操作 |
| `PASS_INTEGRATION` | 与指定 RS485/CAN 对端的联调通过 | 不外推到其他对端或环境 |

状态由工作块根据实际结果人工更新，不建立自动升级状态机。工作块级 `PASS` 只代表其合同内的必需项
通过。失败修复后保留问题结论和必要回归结果，不要求归档每一次中间尝试。

## 3. 最低验收内容

### 3.1 主机测试

记录环境、测试命令或入口、测试计数和结果。失败时保留首个有定位价值的错误及相关源码/测试位置。

### 3.2 交叉构建

记录 Git 提交、Debug/Release 结果和必要的 size。只有固件将用于烧录、需要确认二进制一致性或排查
版本错配时才记录固件 SHA-256。重复成功构建不重复归档日志。

### 3.3 板级测试

记录板卡型号、固件提交或哈希、关键接线/跳线、操作和结果。完整序列号只在确有区分同型号设备的
必要时私有保存；公开记录使用去标识化设备名。

### 3.4 RS485 与 CAN 联调

仅记录影响复现的配置：本端固件、对端类型、波特率/位率、地址或消息 ID、关键接线和结果。只有
出现时序、帧内容、错误计数或互操作问题时才保留抓包或详细日志。

S5-T05 正常通过只保存提交/固件哈希、端口、`19200 8E1`、地址、接线摘要和 H01～H11 状态。失败时
最多增加一条代表性请求/响应、错误类别、当前可能地址和恢复结果；不要求持续抓包或大量重复。

S6-T03 无硬件通过只保存 probe/vcan 结果摘要，不保存 raw frame 历史。实物正常通过只增加 adapter/driver、
500 kbit/s、接线/终端、固件哈希、H01～H08 状态、每个必需周期 ID 的一条代表性解码和接口错误计数差值。
状态事件没有自然变化时允许 `NOT_OBSERVED`；只有失败排障时才在 `.private/can-hil/` 保存短 candump。
CAN revision 1 的七个 ID 均由 STM32 产生，默认固件下的实物 `--observe` 必须保持只读，
不得把这些 ID 当作电脑下发命令使用。H06 的主机到设备物理 ACK 仅使用已审核的静默
`RX_ONLY` 诊断固件执行一次发送；接线摘要必须明确记录 CANH、CANL 和公共 GND。
成功仅证明该对端和接线下的物理收发/ACK，不代表存在应用层命令或回复协议，也不替代
`BUS-02` 双总线并发验收。


### 3.5 长稳与清洁复现

只在后续任务明确要求时执行。持续时间、指标和停止条件由该任务根据实际风险决定，不设统一 24 小时
门槛。成功时保留摘要；失败时只保留有助于定位的资源趋势、错误片段或环境差异。

## 4. 何时建立诊断记录

满足任一条件时，创建一条符合 `diagnostic_record.schema.json` 的 JSON：

- 问题阻塞当前或后续任务，需要跨会话继续；
- 修复后需要明确回归，避免同类故障再次出现；
- 硬件、RS485 或 CAN 问题依赖固件版本、接线或对端配置，简短摘要无法复现。

下列情况不创建诊断记录：立即修正的命令拼写或引号问题、临时路径错误、重复成功运行、无异常的逐条
事件、未影响结论的已知警告。必要时在当前验证记录中写一句说明即可。

## 5. 诊断记录规则

一条记录对应一个值得保留的问题。11 个必需字段说明问题的任务、范围、环境、提交、现象和下一步；
命令、错误片段、工具版本、固件哈希、设备、接线、对端、附件、根因、修复和回归结果均按需填写。

建议私有路径：

```text
.private/diagnostics/<record_id>.json
.private/diagnostics/<record_id>/   # 仅在确有必要时保存日志、抓包或照片
```

不创建空目录，不为正常成功生成占位记录。原始大日志没有排查价值时不长期保存；JSON 中只保留必要的
短错误摘要，附件使用相对路径引用。

## 6. 公开与隐私

公开协议、Schema 和合成示例可以进入 `docs/`。真实诊断记录默认保存在 `.private/diagnostics/`，除非
S7 明确选择并完成去标识化审核。公开内容不得包含：

- Windows/Ubuntu 用户目录或用户名；
- 完整设备序列号；
- 私人 IP、SSID、凭证或访问令牌；
- 购买账户、订单信息；
- 未审核的人像或环境照片。

`.gitignore` 不是唯一保护。用户自行提交前仍需查看建议暂存范围和公开文件内容；Codex 不执行
`git add`、`git commit` 或 `git push`。

## 7. 后续任务使用方式

- S2：只在板级启动、接线或外设问题需要持续排查时建记录；
- S3/S4：主机单测和普通驱动通过只写摘要，复杂并发/数据问题才建记录；
- S5/S6：对端配置、代表性帧和总线错误只在互操作问题中按需保存；正常通过不持续抓包；
- S7：从已审核验证摘要和少量真实问题记录中生成证据矩阵与展示材料。

协议本身通过只说明轻量诊断合同可被后续任务使用，不证明任何后续硬件、总线、长稳或 Release 已通过。
