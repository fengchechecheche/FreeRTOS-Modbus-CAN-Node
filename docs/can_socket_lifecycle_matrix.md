## 1. 目的与声明边界

本记录通过四种 SocketCAN socket 生命周期对照，区分“单 socket”“双 socket 拓扑”和
“临时发送 socket 关闭时机”与 Host 主动 CAN 诊断异常的关系；最后再以产品实际范围执行
“RS485 主动双向轮询 + CAN 被动遥测”并发复验。

前四组属于故障定位，不作为项目必须支持 Host→STM32 CAN 命令的需求扩展。第五组才是当前
产品范围的严格并发准入。测试中看到匹配的 `0x541` 能证明应用往返完成，但不能据此忽略同时
出现的 CAN 错误帧、状态降级或 BUS-OFF。

## 2. 固定环境与方法

| 项目 | 固定值 |
|---|---|
| USB-CAN | `1d50:606f`，原厂 candleLight / `gs_usb` |
| 主机接口 | WSL `can0` |
| CAN 参数 | `500000 bit/s`，Host `sample-point 0.750`，非 CAN FD |
| 接线 | CANH↔CANH、CANL↔CANL、公共 GND |
| 终端 | USB-CAN `120R`；不在测试中改变 |
| NUCLEO 固件 | 上述默认 Debug ELF |
| 周期遥测 ID | `0x240/0x241/0x340/0x341/0x342/0x440` |
| 主机诊断 | Host `0x540` 请求；STM32 `0x541` 应答 |
| 分相 | 0～300 s 被动；300～540 s 主动；540～600 s 恢复 |
| 主动节奏 | 主动阶段第 0/60/120/180 s 各发送一次，sequence/nonce 唯一 |

每组测试前均执行：NUCLEO 断电、`can0 down`、USB-CAN 解除 WSL 挂载、USB-CAN 完全断电
10 秒、只给 USB-CAN 上电、重新挂载并配置接口、确认 `ERROR-ACTIVE` 且错误计数归零，最后才
给 NUCLEO 上电或复位。孤立错误帧、ERROR-WARNING 或 ERROR-PASSIVE 不立即结束测试；接口消失、
遥测持续丢失或反复/持续 BUS-OFF 导致 Host CAN 路径中断时有界停止。

## 4. T1：单 socket 全程长驻

### 4.1 准入

- 用户确认 Shield `PWR` 亮、NUCLEO 已复位且默认固件启动正常。
- USB-CAN 冷启动后，`can0=UP/ERROR-ACTIVE`。
- 基线 `error-warning/error-passive/bus-off` 均为 `0`。
- 5 秒预检连续看到六种周期 ID；没有错误帧。

### 4.2 过程记录

| 时间点 | 观察 |
|---:|---|
| 0～300.057 s | 被动阶段收到 1830 帧；六种周期 ID 全部覆盖；无错误帧，状态保持 `ERROR-ACTIVE` |
| 约 300 s | 第一次 `0x540` 发送返回 16 字节，收到唯一匹配 `0x541`；同时立即出现 `0x2000000C:0000100000000000` 等 BIT1/协议错误帧 |
| 约 360 s | 第二次请求仍收到唯一匹配 `0x541`；累计约 20 个错误帧，接口降为 `ERROR-PASSIVE`，计数增量为 `error-warning +4 / error-passive +3` |
| 约 420 s | 第三次请求仍收到唯一匹配 `0x541`；随后错误帧形成风暴，出现包含 `CAN_ERR_BUSOFF`、`CAN_ERR_ACK`、`CAN_ERR_PROT` 和 `CAN_ERR_CRTL` 组合的多种签名 |
| 420～449.533 s | Host 控制器反复在 `BUS-OFF / ERROR-PASSIVE / ERROR-ACTIVE` 间切换；最高已记录错误帧序号至少为 27721 |
| 449.533 s | 因反复 BUS-OFF 已构成 Host CAN 路径持续中断，人工执行安全停止；未尝试第四次请求，也未进入恢复阶段 |

三次已发送请求的 sequence 为 `0xA1/0xA2/0xA3`，三次均收到一次匹配应答。该事实证明
Host→STM32 接收、应用处理及 STM32→Host 应答在错误发生前后都曾完成，但不能把本轮判为通过。

### 4.4 T1 有界结论

1. “单 socket 从 0 秒持续到 600 秒”不能消除 Host 主动发送时的 BIT1/协议错误和错误风暴。
2. 错误不是由第二个发送 socket 的创建或关闭所必需触发，因为 T1 全程没有第二个 socket。
3. 三次应用应答均成功，因此不能把异常简单描述为“STM32 没有收到请求”或“STM32 没有产生
   应答”。
4. T1 单独不能确定 candleLight 固件、Host 发送完成语义、物理 ACK、适配器状态机或其他因素中
   哪一项是唯一根因；仍需 T2～T4 对照。
5. 本轮因反复 BUS-OFF 安全停止是预定边界，不得写成“完成 10 分钟但存在可接受错误”。

## 5. T2：双 socket 全程长驻

### 5.1 准入与 socket 边界

- USB-CAN 在 T1 后解除挂载并完全断电 10 秒；NUCLEO 和 USB-RS485 保持断电。
- 重新挂载后使用固定 `500000 bit/s / sample-point 0.750`，基线为 `ERROR-ACTIVE`，所有错误
  计数和 RX/TX 包计数为 `0`。
- NUCLEO 上电后，5 秒预检连续看到六种周期 ID；没有错误帧。
- 运行器在计时开始前分别创建一个监控 socket 和一个发送 socket；两个 socket 均保持打开，
  直至安全停止后的统一清理，中途没有创建或关闭第三个 socket。

### 5.5 T2 有界结论

1. 第二个发送 socket 全程保持打开仍不能消除主动发送时的 BIT1/协议错误或第三次请求后的
   BUS-OFF 风暴。
2. T2 全程没有在请求之间关闭发送 socket，因此 T1/T2 已共同反证“只有发送 socket close 才会
   触发错误”的强假设。
3. T2 前两次请求的异常强度低于第三次，说明故障具有累积或状态相关特征；不能仅用一次成功往返
   宣称主动路径稳定。
4. 三次匹配应答和持续周期帧再次证明应用往返能够完成；失败点在于同时发生的 Host CAN 错误状态
   失控，而不是简单的“请求未到达”或“应用未应答”。

## 6. T3：临时发送 socket 立即关闭

### 6.5 T3 有界结论

1. 立即关闭发送 socket 的前两次请求均为零错误，表现优于同一轮次的 T1/T2，但第三次仍发生

   错误状态失控。

## 8. T5：RS485 主动双向轮询 + CAN 被动遥测

### 8.1 准入与权限边界

- USB-CAN 冷启动后保持 `120R`、三线连接，`can0` 按 `500000 bit/s`、`sample-point 0.750`
  配置；新 CH340 USB-RS485 连接为 `/dev/ttyUSB0`。
- NUCLEO 上电并运行上述默认固件；CAN 5 秒预检覆盖六种周期 ID，错误计数为零。
- 项目三既有 x86_64 release 程序使用地址 4 实物 profile。首次以 `iot-gw` 用户启动时，因该用户
  不在 `dialout` 组而在打开串口前失败；`/dev/ttyUSB0` 为 `root:dialout 0660`。同一二进制和
  profile 改由 WSL `root` 启动后，短预检完成 83 次成功请求、零失败。
- 因此正式测试固定以 WSL `root` 启动网关。该处记录的是主机权限边界，不是 STM32、Shield、
  RS485 物理链路或 Modbus 协议失败。

### 8.4 T5 有界结论

1. 在产品实际范围内，RS485 主机请求/STM32 响应与 STM32 CAN 周期遥测可以并发保持至少
   10 分钟；期间 CAN 无错误帧、状态降级或 BUS-OFF，RS485 无请求失败。
2. T5 证明的是“RS485 主动双向管理 + CAN 单向遥测发布”的产品链路，不声称 Host→STM32
   CAN 诊断命令稳定。
3. `iot-gw` 用户缺少 `dialout` 权限需要在部署前通过用户组或设备规则修复；本轮以 root 运行
   只用于保持现有硬件验证连续性，不能把 root 作为最终部署要求。

## 9. 最终横向结论

| 路线 | 结果 | 结论 |
|---|---|---|
| T1：单 socket 长驻 | `FAIL` | 第三次主动请求后发生严重错误风暴 |
| T2：监控与发送 socket 均长驻 | `FAIL` | 发送 socket 从未关闭仍发生错误风暴 |
| T3：发送后立即关闭 | `FAIL` | 前两次零错误，第三次仍发生错误风暴 |
| T4：计划延迟 5 秒关闭 | `FAIL` | 第一次请求后、close 发生前已进入 BUS-OFF |
| T5：RS485 主动双向 + CAN 被动遥测 | `PASS` | 完整 600 秒产品范围并发稳定 |

综合证据支持以下结论：

1. `close()` 不是主动 CAN 异常的必要触发条件。单 socket、两个全程长驻 socket、立即关闭和
   尚未关闭四种情形均可能失败；不得再把问题表述为“发送 socket 一关闭就必然触发”。
2. T1～T4 均曾取得匹配的 `0x541`，说明 Host 请求、STM32 接收/处理和应用应答可以完成；失败
   位于 Host 主动发送参与时出现的适配器/控制器错误状态失控，而不是简单的应用层无响应。
3. 当前证据尚不足以把错误唯一归因于 candleLight 固件、`gs_usb`、适配器硬件或某个具体
   控制器状态机缺陷。能够排除的是“必须由第二个 socket 创建/关闭触发”这一窄假设。
4. T5 将异常隔离在已经降级为非发布阻塞项的 Host→STM32 CAN 诊断路线之外，并证明产品所需
   的 RS485 双向管理和 CAN 遥测能够稳定并发。因此该异常不再阻止项目三/项目五继续推进，
   但也不能据此宣称 Host 主动 CAN 诊断已修复。
